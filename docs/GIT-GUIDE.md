# Git / GitHub 실전 가이드 (팀용)

Git을 처음 쓰는 팀원을 기준으로 쓴 문서입니다. **개념보다 "이럴 땐 이 명령어"** 위주입니다.
외울 필요 없습니다. 필요할 때 이 문서를 열어서 복사해서 쓰세요.

- 협업 규칙(브랜치 이름, 커밋 형식)은 [CONVENTIONS.md](CONVENTIONS.md)에 있습니다.
- 이 문서는 **그 규칙을 실제로 어떻게 실행하는지**를 다룹니다.

---

## 0. 왜 브랜치를 쓰나 (3줄 요약)

브랜치가 없으면 두 사람이 같은 파일을 동시에 고쳤을 때 **나중에 올린 사람이 앞사람 작업을 덮어씁니다.**
브랜치는 각자 **작업용 복사본**을 만들어 주는 기능입니다. 각자 자기 복사본에서 안전하게 작업하고, 다 되면 합칩니다.

> **결론: 브랜치를 쓰면 같은 시간에 같은 프로젝트를 건드려도 서로 안 망가집니다.**

```
main  ─────●────────────────●────  ← 항상 동작하는 버전
            \              /
   내 브랜치  ●──●──●──────●        ← 내가 작업하는 곳 (남에게 영향 없음)
```

---

## 1. 핵심 개념 5개만

| 용어 | 한 줄 설명 | 비유 |
|---|---|---|
| **repository (저장소)** | 프로젝트 전체 + 모든 변경 기록 | 프로젝트 폴더 |
| **commit (커밋)** | "여기까지 했다"고 기록을 남기는 것 | 게임 세이브 |
| **branch (브랜치)** | 작업용 복사본 | 세이브 파일 슬롯 |
| **push / pull** | 내 PC ↔ GitHub 로 올리기 / 받기 | 클라우드 업로드/다운로드 |
| **PR (Pull Request)** | "내 작업을 main에 합쳐주세요" 요청 | 결재 올리기 |

**기억할 것 하나**: 커밋은 **내 PC에만** 저장됩니다. `push` 를 해야 GitHub에 올라가고 팀원이 볼 수 있습니다.

## 2. 최초 1회 세팅

각자 PC에서 **딱 한 번만** 하면 됩니다.

### 2-1. Git 설치 확인

```bash
git --version
```

버전이 안 나오면 [git-scm.com](https://git-scm.com/downloads)에서 설치하세요.

### 2-2. 내 정보 등록 (커밋에 이름이 찍힙니다)

```bash
git config --global user.name "본인이름"
```

```bash
git config --global user.email "GitHub에_가입한_이메일"
```

> 이메일은 **GitHub 가입 이메일과 같아야** 커밋이 본인 계정에 연결됩니다.

### 2-3. 프로젝트 내려받기

```bash
git clone https://github.com/lellon0403/MetroTrip.git
```

```bash
cd MetroTrip
```

### 2-4. 환경변수 파일 만들기

`frontend/.env`는 GitHub에 올라가지 않습니다(키 노출 방지). **각자 직접 만들어야 합니다.**
팀에서 공유받은 카카오 키를 `frontend/.env` 파일로 저장하세요. 자세한 건 [README](../README.md) 참고.

## 3. 매일 하는 작업 흐름 (이것만 반복)

**작업 하나 = 브랜치 하나 = PR 하나** 입니다.

### ① 최신 코드 받기 (작업 시작 전 항상)

```bash
git checkout main
```

```bash
git pull
```

> ⚠️ **이걸 건너뛰면 충돌이 납니다.** 매번 하세요.

### ② 브랜치 만들기

```bash
git checkout -b feat/fe-station-list
```

이름 규칙은 [CONVENTIONS.md](CONVENTIONS.md) 2장 참고. (`feat/fe-무엇` 형태)

### ③ 코드 작업

평소대로 파일을 수정합니다. 지금 어떤 상태인지 궁금하면:

```bash
git status
```

### ④ 커밋 (작게, 자주)

```bash
git add .
```

```bash
git commit -m "feat: 역 목록 컴포넌트 추가"
```

> 기능 하나 끝날 때마다 커밋하세요. "하루치 몰아서 1커밋"은 나중에 문제 찾기가 지옥이 됩니다.

### ⑤ GitHub에 올리기

처음 올릴 때 (브랜치를 새로 만든 경우):

```bash
git push -u origin feat/fe-station-list
```

두 번째부터는:

```bash
git push
```

### ⑥ PR 만들기

1. GitHub 저장소 페이지에 들어가면 **"Compare & pull request"** 버튼이 뜹니다. 클릭.
2. 제목: 커밋 메시지와 같은 형식
3. 본문에 3가지 작성:
   - 무엇을 했는지
   - 어떻게 확인했는지 (브라우저 스크린샷)
   - 관련 문서 (`docs/SPEC.md`의 어떤 항목인지)
4. **Create pull request** 클릭
5. 팀원 1명 리뷰 후 **Squash and merge** 로 병합

### ⑦ 병합 후 정리

```bash
git checkout main
```

```bash
git pull
```

```bash
git branch -d feat/fe-station-list
```

## 4. 명령어 치트시트

| 하고 싶은 것 | 명령어 |
|---|---|
| 지금 상태 확인 | `git status` |
| 내가 어느 브랜치에 있지? | `git branch` |
| 최신 코드 받기 | `git pull` |
| 브랜치 새로 만들고 이동 | `git checkout -b 브랜치이름` |
| 기존 브랜치로 이동 | `git checkout 브랜치이름` |
| 변경사항 담기 | `git add .` |
| 커밋 | `git commit -m "메시지"` |
| 올리기 | `git push` |
| 커밋 기록 보기 | `git log --oneline -10` |
| 내가 뭘 바꿨는지 보기 | `git diff` |

## 5. 충돌(conflict)이 났을 때

**충돌은 잘못이 아닙니다.** 두 사람이 같은 줄을 고쳤을 때 Git이 "누구 걸 쓸지 모르겠다"고 물어보는 것뿐입니다.

### 이렇게 생겼습니다

```
<<<<<<< HEAD
const RADIUS = 1000;
=======
const RADIUS = 500;
>>>>>>> feat/fe-map
```

- `<<<<<<< HEAD` ~ `=======` : **원래 있던 내용**
- `=======` ~ `>>>>>>>` : **내가 가져온 내용**

### 해결 순서

1. 파일을 열어서 **남길 코드만 남기고** `<<<<<<<`, `=======`, `>>>>>>>` 세 줄을 **전부 지웁니다.**
2. 저장 후:

```bash
git add .
```

```bash
git commit -m "fix: 충돌 해결"
```

```bash
git push
```

> **혼자 판단하지 마세요.** 남의 코드가 걸려 있으면 Discord에서 "이 줄 누가 고쳤어요?" 물어보고 정하세요.
> 잘못 지우면 남의 작업이 사라집니다.

## 6. 사고 났을 때 복구법

Git은 **커밋만 했다면 거의 다 되돌릴 수 있습니다.** 당황하지 마세요.

### 아직 커밋 안 한 변경을 전부 버리고 싶다

```bash
git restore .
```

> ⚠️ 되돌릴 수 없습니다. 정말 버릴 때만.

### 방금 한 커밋 메시지를 잘못 썼다 (아직 push 전)

```bash
git commit --amend -m "올바른 메시지"
```

### 방금 커밋을 취소하고 싶다 (변경 내용은 유지, 아직 push 전)

```bash
git reset --soft HEAD~1
```

### main에서 작업해버렸다 (브랜치 만드는 걸 깜빡함)

아직 커밋 전이라면 그냥 브랜치를 만들면 됩니다. 변경사항이 따라옵니다.

```bash
git checkout -b feat/fe-작업이름
```

### push 했더니 "rejected" 라고 나온다

내가 작업하는 동안 남이 먼저 올린 겁니다. 받아서 합친 뒤 다시 올립니다.

```bash
git pull
```

(충돌이 나면 5번 참고) 그 다음:

```bash
git push
```

### 완전히 꼬였다

**가장 안전한 방법**: 지금 폴더를 통째로 다른 이름으로 복사해서 백업해두고, 새로 clone 받으세요.
그리고 Discord에 상황을 공유하세요. 억지로 되돌리다 남의 커밋을 날리는 게 제일 위험합니다.

## 7. 절대 하지 말 것

| 금지 | 이유 |
|---|---|
| `main`에 직접 push | 팀 전체가 깨질 수 있음. 반드시 브랜치 + PR |
| `git push --force` | **남의 커밋이 영구 삭제됩니다.** 쓰지 마세요 |
| `frontend/.env` 커밋 | 카카오 API 키 노출. 이미 `.gitignore`에 있지만 `git add` 강제 금지 |
| 확인 안 하고 커밋 | 브라우저에서 동작 확인 후 커밋 |
| 남의 브랜치에 커밋 | 각자 브랜치에서 작업 |

### 만약 `frontend/.env`나 키를 실수로 올렸다면

1. **즉시 Discord에 공유** (숨기면 더 큰일 납니다)
2. 카카오 개발자 콘솔에서 **키 재발급**
3. 파일을 지우는 것만으로는 기록에 남아 있으니, 키 재발급이 핵심입니다

## 8. 명령어가 어렵다면 — GitHub Desktop

터미널이 부담스러우면 **GitHub Desktop**(무료 GUI)을 쓰세요. 결과는 똑같습니다.

[desktop.github.com](https://desktop.github.com/) 에서 설치 후:

| 할 일 | GitHub Desktop에서 |
|---|---|
| 최신 코드 받기 | 상단 **Fetch origin** → **Pull origin** |
| 브랜치 만들기 | 상단 Current Branch → **New Branch** |
| 커밋 | 좌측에서 파일 체크 → 하단에 메시지 입력 → **Commit** |
| 올리기 | 상단 **Push origin** |
| PR 만들기 | **Create Pull Request** (브라우저로 연결됨) |

> 팀원 중 일부가 Desktop, 일부가 터미널을 써도 **전혀 문제없습니다.** 같은 Git입니다.

## 9. 팀 규칙 요약 (이 4줄만 지키면 안 꼬입니다)

1. 작업 전 **`git pull`**
2. **브랜치 만들고** 작업 (main에서 직접 X)
3. 작업 끝나면 **push → PR**
4. 헷갈리면 **멈추고 Discord에 물어보기** (혼자 해결하려다 사고가 커집니다)
