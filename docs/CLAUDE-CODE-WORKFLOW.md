# Claude Code 협업 워크플로

이 프로젝트는 대부분의 작업을 **Claude Code로** 진행합니다.
여러 PC에서 각자 Claude Code를 돌리면서도 서로 꼬이지 않게 하는 방법을 정리합니다.

- Git 자체가 처음이라면 → [GIT-GUIDE.md](GIT-GUIDE.md) 먼저
- 팀 규칙(브랜치 이름, 커밋 형식) → [CONVENTIONS.md](CONVENTIONS.md)

---

## 1. Claude Code가 할 수 있는 것 / 없는 것

먼저 오해를 없애고 시작합시다.

### ✅ 할 수 있는 것

- 브랜치 생성 / 전환 (`git checkout -b`)
- 커밋, 푸시
- PR 생성 (`gh` CLI 설치 시)
- `git fetch` 후 **"develop이 3커밋 앞서 있으니 pull 하는 게 좋겠다"** 고 알려주기
- 충돌 해결 도와주기

### ❌ 할 수 없는 것

| 못 하는 것 | 이유 |
|---|---|
| **먼저 말 걸기** | 사용자가 입력할 때만 동작합니다. 백그라운드 감시 불가 |
| **"지금 머지할 타이밍이에요" 알림** | 위와 같은 이유. **물어봐야 확인해 줍니다** |
| 다른 팀원이 지금 뭘 하는지 알기 | `git fetch`로 **이미 push된 것**만 볼 수 있음. 로컬 작업은 못 봄 |
| 지난 세션 기억 | 세션이 끝나면 대화는 사라집니다 (파일과 커밋은 남음) |

### 그래서 이렇게 씁니다

> **머지 타이밍은 Claude가 알려주는 게 아니라, 세션 시작할 때 "확인해줘"라고 시키는 것입니다.**

이 프로젝트에는 루트에 [`CLAUDE.md`](../CLAUDE.md) 파일이 있고,
Claude Code가 **세션마다 자동으로 읽습니다.** 거기에 "세션 시작 시 `git fetch`로 확인하라"고 적어뒀기 때문에
팀원 누구의 PC에서든 같은 규칙으로 동작합니다.

## 2. 하루 작업 흐름 (Claude Code 기준)

### ① 세션 시작 — 상태 확인부터

Claude에게 이렇게 말하세요:

```
작업 시작할게. git fetch 해서 지금 상태 확인해줘.
develop보다 뒤처져 있으면 알려주고.
```

Claude가 확인하고 "origin/develop이 2커밋 앞서 있습니다" 같이 알려줍니다.

### ② 브랜치 만들고 시작

```
feat/fe-station-list 브랜치 만들고 시작해줘.
역 목록 UI 작업을 할 거야. 관련 현재 문서와 구현을 먼저 확인해줘.
```

> 브랜치 이름을 직접 정하기 어려우면 **"작업용 브랜치 만들어줘"** 라고만 해도 규칙에 맞게 지어줍니다.

### ③ 작업

평소처럼 요청합니다. 다만 **범위를 벗어나면 짚어달라고** 해두면 좋습니다.

```
역 목록 컴포넌트 만들어줘. 요청 범위 밖이면 먼저 말해줘.
```

### ④ 동작 확인 (건너뛰지 마세요)

```
브라우저에서 실제로 동작하는지 확인해줘.
```

> 코드가 그럴듯해 보여도 지도가 안 뜨는 경우가 흔합니다. **확인 전에는 커밋하지 마세요.**

### ⑤ 커밋 & 푸시 & PR

```
여기까지 커밋하고 푸시한 다음 PR 올려줘.
```

Claude가 커밋 메시지를 규칙에 맞게 써주고, PR 본문도 채워줍니다.
**내용을 한 번 읽어보고** 승인하세요. 그대로 팀에 올라갑니다.

### ⑥ 세션 끝낼 때

```
현재 변경, 검증 결과, 남은 사항을 정리해줘.
```

> 다음에 **다른 PC에서 이어서 작업할 때** 커밋과 PR 설명이 맥락을 전달합니다.

## 3. 머지 타이밍은 이렇게 판단합니다

Claude가 먼저 알려주지 못하므로, **다음 세 시점에 직접 물어보세요.**

| 시점 | Claude에게 할 말 |
|---|---|
| 작업 시작할 때 | `git fetch 하고 develop이랑 차이 있는지 알려줘` |
| 기능 하나 끝났을 때 | `이 정도면 PR 올려도 될까? 커밋 내역 정리해줘` |
| PR 올리기 전 | `develop 최신 내용 받아서 충돌 없는지 확인해줘` |

### 언제 PR을 올리나

**"기능 하나가 동작하면"** 올립니다. 완벽할 때까지 기다리지 마세요.

- ❌ 나쁜 예: 3일 동안 혼자 작업 → 한 번에 PR (충돌 지옥)
- ⭕ 좋은 예: 역 목록 완성 → PR / 지도 이동 완성 → PR

> 브랜치를 오래 들고 있을수록 충돌이 커집니다. **작게 자주 합치는 게 안전합니다.**

---

## 4. 여러 PC에서 동시에 쓸 때 주의사항

각 PC의 Claude Code는 **서로를 전혀 모릅니다.** 각자 자기 폴더만 봅니다.

### 반드시 지킬 것

1. **작업 시작 전 `git pull`** — Claude에게 시켜도 되고 직접 해도 됩니다
2. **작업 끝나면 바로 push** — 로컬에 며칠씩 들고 있지 않기
3. **같은 파일을 동시에 고치지 않기** — 이슈·PR·팀 채널에 미리 공유하기
4. **`CLAUDE.md`를 고쳤으면 팀에 공유** — 팀 전체 Claude 동작이 바뀝니다

### 자주 나는 사고

| 상황 | 원인 | 예방 |
|---|---|---|
| 같은 기능을 두 명이 각각 구현 | 누가 뭘 하는지 몰라서 | 이슈·PR + 팀 채널 공유 |
| Claude가 남이 만든 파일을 다시 만듦 | pull을 안 해서 최신 코드를 모름 | 세션 시작 시 `git pull` |
| 충돌이 산더미 | 브랜치를 너무 오래 들고 있음 | 작게 자주 PR |
| 스타일이 제각각 | 각 PC에서 Claude가 다르게 판단 | `CLAUDE.md`에 규칙 명시 |

## 5. Claude에게 시킬 때 요령

### 범위를 항상 명시하세요

Claude는 시키면 시키는 대로 만듭니다. 범위를 안 정해주면 **필요 없는 기능까지 만듭니다.**

```
❌ 지하철 앱 만들어줘
⭕ 역 목록 UI와 관련 테스트만 수정해줘. 그 외에는 건드리지 마.
```

### 범위 밖 제안은 거절하세요

Claude가 "로그인 기능도 추가할까요?" 같은 제안을 하면 지정 범위에 포함할지 먼저 확인하세요.
현재 범위는 루트 [README](../README.md)와 관련 파트 문서를 기준으로 확인합니다.

### 문서를 먼저 고치게 하세요

범위가 바뀌면 이렇게 말하세요.

```
이 기능 추가하려는데, 루트 README와 관련 파트 문서부터 고치고 시작하자.
```

> 코드만 바뀌고 문서가 그대로면, 다른 PC의 Claude는 **옛날 문서를 읽고** 다르게 작업합니다.

### 확인 없이 믿지 마세요

- 생성된 코드는 **브라우저/실행 화면에서 직접 확인**
- "완료했습니다"를 그대로 믿지 말고 **눈으로 확인**
- 특히 외부 API(카카오)는 키·도메인 설정 문제로 자주 실패합니다

## 6. 자주 쓰는 프롬프트 모음

복사해서 쓰세요.

**작업 시작**
```
git fetch 해서 현재 상태 확인하고, develop보다 뒤처져 있으면 알려줘.
그 다음 feat/fe-<작업이름> 브랜치 만들고 시작하자.
```

**작업 지시**
```
<기능>과 관련 테스트만 작업해줘.
지정한 범위를 벗어나는 건 먼저 물어보고.
```

**중간 점검**
```
지금까지 뭘 바꿨는지 정리해서 보여줘. 커밋할 단위로 나눠서.
```

**마무리**
```
브라우저에서 동작 확인하고, 문제없으면 커밋해줘.
그 다음 푸시하고 PR 올려줘. PR 본문에 확인한 내용도 적어주고.
```

**세션 종료**
```
오늘 한 것 / 검증한 것 / 남은 것을 3줄로 정리해줘.
```

**사고 났을 때**
```
git 상태가 꼬인 것 같아. 지금 상황 설명해주고,
되돌릴 방법을 위험한 순서대로 알려줘. 바로 실행하지는 말고.
```

> 마지막 프롬프트의 **"바로 실행하지는 말고"** 가 중요합니다.
> Git 사고 복구는 잘못하면 남의 커밋을 날립니다. 설명을 먼저 듣고 판단하세요.
